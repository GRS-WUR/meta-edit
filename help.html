How to fill in the metadata form

This form describes a dataset so others can find it, understand it and reuse it. The result is a small text file (a Metadata Control File, .yml) that you keep next to your data.

Form: https://grs-wur.github.io/meta-edit/ · Online version of this guide: https://grs-wur.github.io/meta-edit/help.html

Nothing is saved automatically. Your entries live only in this browser tab until you click Save. Save often, and always before closing the tab.

Getting started

  1. Start a record. The form opens with an empty record and GRS defaults already filled in. To continue an earlier record, use File → Open and choose its .yml file.
  2. Give it an identifier in the first step, Metadata. This becomes the file name.
  3. Work through the steps from top to bottom. At minimum, fill in the fields marked Required in this guide.
  4. Click Save. Your browser downloads <identifier>.yml.
  5. Store the file with your data, for example in the same project folder, repository or archive deposit.

Using the form

  • Steps: the form is divided into steps. Click a step's title to open it. You can move between steps in any order.
  • Help text: each field has a short explanation in the form itself. This page gives more detail and examples.
  • Lists: some sections hold several entries (contacts, keyword groups, distributions, platforms, attributes). Use the + button to add an entry and the bin icon to remove one.
  • Dropdowns: fields with a fixed set of options show a dropdown. This page explains which option to pick.
  • Dates: click a date field to pick from a calendar. Dates are saved as YYYY-MM-DD.
  • Empty fields are fine. They are still written to the file, so they can be filled in later.
  • File → New clears the form and starts again from the defaults. Save first if you want to keep what you entered.

The fields, step by step

Examples come from a real record: UAV measurements of sun-induced chlorophyll fluorescence over potato and sugar beet fields, published on 4TU.ResearchData. Fields marked Pre-filled already have a sensible default for GRS datasets; check it, and change it only if needed.

1. Metadata

Information about this metadata record itself, not about the data.

Identifier Required

A short, unique name for the record. It becomes the file name, so use letters, numbers and hyphens, without spaces. A project name plus data type works well. Students: use the ID given by the data steward.

Example: 4TU-UAV-SIF-test

Language Pre-filled

Two-letter code of the language you write this record in.

Example: en

Alternate language

Only if you also describe the dataset in a second language, e.g. nl. Otherwise leave empty.

Character set Pre-filled

Leave as utf8.

Parent identifier

The larger record or publication this dataset belongs to, such as the DOI of the published dataset or the project's record. Students: your supervisor's last name.

Example: DOI:10.4121/20348382.v1

Hierarchy level Required Pre-filled

What the record describes. Almost always dataset. Use series for a collection of related datasets, software or model for code.

Metadata dates

Creation is the date you made this record and is filled in with today's date for a new record. Set Revision when you update the record later.

Dataset URI

A persistent web address for the dataset, if it has one. Often left empty.

2. Spatial information

How the data represent geographic space.

Data type Pre-filled

grid for rasters and imagery (UAV, satellite), vector for points, lines or polygons, textTable for tables with coordinates.

Example: grid

Geometry type Pre-filled

For imagery choose surface. For vector data choose the shape used: point, curve (lines) or surface (polygons).

3. Identification

What the dataset is, when it was made, where it covers, and how it may be used. This is the most important step.

Dataset language Pre-filled

Language of any text inside the data (labels, column names). Two-letter code.

Title Required

The name of the dataset. Make it descriptive enough to recognise in a search result: what, where, and, if relevant, how. For thesis data, the thesis title works.

Example: Diurnal UAV-based sun-induced chlorophyll fluorescence over potato and sugar beet fields

Abstract

A short paragraph on what was measured or produced, where, when, and with which instruments or methods. Someone should be able to decide from this alone whether the data are useful to them.

Example: UAV-based sun-induced chlorophyll fluorescence was acquired over potato and sugar beet fields during clear sky conditions on August 2, 2018. Four flights following a diurnal cycle were carried out…

Edition

A version number, if the dataset has versions. Otherwise leave empty.

Dataset dates

Fill in at least one. Creation: when the data were collected or produced. Publication: when they were published, e.g. in a repository. Revision: when they were last changed.

Example: creation 2018-08-02, publication 2022-08-23

Keywords

Words that help people find the dataset. Click + to add a keyword group, then type each keyword and press Enter. Choose the keyword type: theme for subjects (most keywords), place for locations, discipline for research fields. If the keywords come from a controlled list, such as a thesaurus, enter its name and link under Vocabulary.

Illustrative: a theme group with chlorophyll fluorescence, UAV, potato, sugar beet and a place group with Netherlands

Topic categories

One or more broad, standard categories used by catalogues. For GRS data, common choices are imageryBaseMapsEarthCover, farming, environment, biota and elevation.

Extents → Spatial Pre-filled

The area covered, as a bounding box of four numbers in this order: minimum longitude, minimum latitude, maximum longitude, maximum latitude. Type each number and press Tab to move to the next. Keep CRS as 4326 (longitude/latitude in degrees, WGS 84) unless you know otherwise. The default covers the whole of the Netherlands; narrow it to your study area if you can.

Default: 3.356, 50.75, 7.218, 53.563 · Find a bounding box on a map (choose the CSV output)

Extents → Temporal

The period the data cover: Begin and End dates. For a single day, use the same date for both. Resolution is optional: the time step of the data as an ISO 8601 duration, such as P1D (daily) or PT1H (hourly).

Access constraints Pre-filled

Choose license when the data are shared under a license (the usual case). Choose otherRestrictions if there are no special constraints, or restricted if access is limited.

License Pre-filled

The license name and a link to its text. The default, CC BY 4.0, lets anyone reuse the data with attribution. Change it if your data were published under a different license.

Example: CC BY 4.0, https://creativecommons.org/licenses/by/4.0

Rights

An optional rights statement, such as the copyright holder and year.

Dataset URL

The landing page of the dataset, if it has one, e.g. its repository page.

Browse graphic

A link to a small preview image of the data, such as a quicklook map or a thumbnail of an orthomosaic. Use a web link to a PNG or JPG.

Status Pre-filled

completed for finished datasets, onGoing if data are still being added, planned if they don't exist yet.

Maintenance frequency Pre-filled

How often the data will be updated. asNeeded suits most research data; use notPlanned if they will never change.

4. Content information

What is inside the data: the variables and, for imagery, the spectral bands.

Content type Pre-filled

image for imagery (UAV, satellite, camera), coverage for other gridded data such as model output, feature_catalogue for vector data.

Processing level

For imagery, the processing level if one applies, e.g. L1 for radiometrically corrected or L2 for reflectance products.

Attributes

One entry per variable in the data (a column, band or layer). Name: exactly as it appears in the data. Title: a readable name. Data type: usually number for measurements. Units: SI units. URL: optional link to a definition.

Illustrative: name SIF, title Sun-induced fluorescence, type number, units mW m-2 sr-1 nm-1

Dimensions

For imagery: one entry per spectral band, with its name, units and lower and upper wavelength. Leave empty for non-imagery data.

Illustrative: green, nm, min 530, max 570

5. Distribution information

Where the data can be found or downloaded. Add one entry per location.

URL Required

The web address of the data or their landing page. A DOI link also works.

Example: https://data.4tu.nl/datasets/25a3055f-4d04-4791-9591-83bbca27a13c/1

Type Pre-filled

WWW:LINK for a web page or repository. The other options are for web services, such as OGC:WMS for a map service.

Name

Name of the repository or service.

Example: 4TU.ResearchData

Description

A sentence about what is found at this location, e.g. "Full dataset with raw and processed images". It is saved in the record's language.

Function Pre-filled

download if the data can be downloaded there; information for a page that only describes them; order if access must be requested.

6. Contact information

Who is responsible for the data. Add one entry per person or role.

Role Required Pre-filled

What this contact does. owner: who owns the data (usually the PI or supervisor). pointOfContact: whom to ask about the data. originator or author: who collected or created the data. principalInvestigator: the project lead. Use each role once; if two people share a role, the second is saved as e.g. owner_2.

Organization Required Pre-filled

The responsible organisation; GRS unless otherwise specified.

Name and position

The responsible person and their position, e.g. Associate Professor.

Example: Lammert Kooistra

Email Required

A contact email address. Prefer an address that will remain valid; a student's university address expires after graduation, so add the supervisor as a second contact.

Other contact details

URL, phone, fax, address, city, administrative area (province), postal code and country. Fill in what is useful. City and country are pre-filled with Wageningen, Netherlands, and the URL with the GRS website.

Contact instructions

Optional: when or how to get in touch, e.g. "Contact by email".

7. Acquisition

The platforms and instruments used to collect the data. Add one entry per platform; each platform can have several instruments.

Platform and description

The name of the platform (drone, aircraft, satellite, field station) and what kind it is.

Example: Dji Mavic2, Quadcopter

Instruments

The sensors carried by the platform: name and type.

Example: Parrot Sequoia, MSP sensor (multispectral)

For data not collected with an instrument, such as model output, leave this step empty.

8. Data quality

How the data were produced, so others can judge whether to trust and reuse them.

Scope → Level Pre-filled

What the quality statement applies to. Leave as dataset.

Lineage statement

A few sentences on how the dataset was made: source data, processing steps, software and versions, and any calibration or quality checks. This is one of the most useful fields for anyone reusing your data.

Illustrative: Images were calibrated with a reflectance panel, mosaicked in photogrammetry software (name and version), and resampled to 5 cm resolution.

Importing instead of typing

If the dataset is already described elsewhere, you can pre-fill the form:

  • File → Import, then DOI: enter the DOI, e.g. 10.4121/20348382.v1. Title, authors, publisher, publication date and keywords are filled in from the DOI registration.
  • File → Import, then iso19139: give a link to, or upload, an ISO 19139 XML metadata record.
  • File → Import from WMS: enter a web map service address, pick a layer, and its title, description, keywords, extent and contact are filled in.

Imported values are added to what is already in the form; nothing else is cleared. Imports never fill in everything, so check each step afterwards. Importing uses an external conversion service, so it needs an internet connection and may occasionally be unavailable.

Exporting to other formats

File → Export converts the record to another standard for repositories and catalogues that require it: iso19139 (XML), oarec-record (OGC API - Records), stac-item (STAC) or dcat. Always keep the .yml file from Save as your master copy: it is the only format you can open and edit again in this form.

Sharing a record

If your .yml file is online, for example on GitHub (use its Raw link), anyone can open it in the form with a link like this:

https://grs-wur.github.io/meta-edit/?mcf=<link to the .yml file>

Common questions

I closed the tab. Is my work lost?
Yes, unless you saved it. The form keeps nothing in the browser. Save regularly; you can always reopen the file with File → Open.
The file is called metadata.yml instead of my identifier.
The Identifier field in the Metadata step was empty when you saved. Fill it in and save again.
Which fields do I really need?
The ones marked Required: identifier, hierarchy level, title, at least one contact (role, organisation, email) and the URL of each distribution. A good title, abstract, keywords, extent and lineage make the record much more useful, so fill those in too.
I opened an older record and some fields look different.
Records made with an earlier version of the form are converted automatically. For example, the license is split into name and link. Check the fields and save; the new file uses the current format.
The form looks out of date after an update.
Your browser may be showing a cached copy. Reload with Ctrl + Shift + R (Cmd + Shift + R on a Mac).
Import or Export shows an error.
The conversion service may be temporarily unavailable. Try again later; opening and saving .yml files always works.
